# CLAUDE.md - Memory & Project Documentation

## 🏷️ Project Overview
**PROFAS Leadership LMS** - Executive Leadership Academy & Learning Management System.
- **Type**: SaaS Learning Management System (LMS) / Interactive E-Learning Platform.
- **Tech Stack**: Next.js 15 (App Router), React 19, TypeScript, Tailwind CSS / Vanilla CSS, Prisma ORM, NextAuth.js / Google OAuth, Vercel Serverless.
- **Current Status**: Live on Vercel Production (`https://profas-leadership-lms.vercel.app`) with dynamic Google OAuth callback and serverless SQLite auto-copying to `/tmp`.

## 🛠️ Essential Commands
- **Local Development**: `npm run dev` (Runs on port 3000)
- **Build**: `npm run build` (Executes Prisma generate, schema push, seeding, and Next.js production build)
- **Typecheck**: `npm run typecheck`
- **Lint**: `npm run lint` (auto-fix mechanical issues: `npm run lint:fix`)

- **Smoke Test**: `npm run smoke`
- **Autopilot Loop**: `npm run autopilot:start` / `npm run autopilot:status`

## 🎨 Architectural & Style Guidelines
1. **Frontend Design**:
   - Prioritize modern **Glassmorphism** aesthetics (`backdrop-blur-md`, subtle semi-transparent borders, glowing gradients).
   - Dynamic dark/light mode compatibility.
   - Smooth micro-animations and responsive layouts.
2. **Backend & Database**:
   - Prisma ORM managing relational entities (User, Course, CourseNode, Assessment, Certificate, Enrollment).
   - Serverless compatibility: SQLite database (`dev.db`) is automatically copied to `/tmp/dev.db` in serverless environments (Vercel/AWS Lambda) to avoid read-only filesystem errors.
   - Prepared for future migration to Cloud PostgreSQL (Neon/Supabase).
3. **Coding Standards**:
   - Modular, clean TypeScript code with strict typing.
   - Avoid ad-hoc utility clutter; leverage reusable design tokens and components.
   - Preserve existing documentation and docstrings.
4. **Folder Structure** (adapted from standard React layout to Next.js App Router — `app/` stays at root for routing):
   - `app/` — routes only (App Router convention, cannot move).
   - `components/ui/` — small, reusable presentational components (Header, Footer, Logo, cards, chrome).
   - `components/shared/` — feature/business-logic components (CoursePlayer, Quiz, admin/mentor panels, export buttons).
   - `services/` — DB client, auth, rate-limit, uploads, and `services/export/` (docx/pdf/pptx/xlsx generators).
   - `utils/` — small pure helper functions.
   - `hooks/` — reusable client-side React hooks (e.g. `useLocalBackup`).
   - `context/` — reserved for React Context providers (empty until a real cross-cutting client state need appears).
   - `types/` — shared TypeScript types not already covered by Prisma-generated types.
   - `constants/` — reserved for cross-cutting constants (domain enums live in `prisma/schema.prisma` instead).
   - `styles/` — global CSS, imported from `app/layout.tsx`.

## 🔄 Self-Improvement & Progress Log
- **2026-07-26 [Phase 13 - Real Login Streak]**: Fourth autonomous feature cycle. Found an even more blatant fake-data case than Phase 12: the dashboard header unconditionally showed "7 hari beruntun" (7-day streak) for every single user, hardcoded, regardless of any real activity — a first-time login would falsely claim a week-long streak. Added `services/streak.ts` (`getLoginStreak`), which computes a real consecutive-day streak from `ActivityLog` `USER_LOGIN` entries (already logged on every local + Google OAuth login, just never used for this). `DashboardChrome` is now an async server component that fetches the real streak and passes it to `DashboardChromeClient`; the badge only renders when the streak is actually ≥ 1 day, instead of always showing a fake number. Verified with typecheck, lint, `dup:check`, and a full production build (54/54 routes, no bundle size regressions).
  - **Backlog (needs schema work, deferred per current DB-work pause)**: `app/program/[slug]/page.tsx` also displays `course.rating` (a star rating) next to a hardcoded literal `"(128 ulasan)"` — that review count is not computed from anything, it's a fixed string in the JSX for every course. There is no review/rating model in `prisma/schema.prisma` at all, so a real fix needs a new table (e.g. `CourseReview`) to actually collect and aggregate ratings — out of scope while database changes are paused. Flagging here so it isn't lost.
- **2026-07-26 [Phase 12 - Fix Fake Student Count]**: Third autonomous feature cycle. Found a real data-integrity bug rather than another notification gap: `Course.studentsCount` — the "X peserta" social-proof number shown on every program detail/catalog/dashboard card — was only ever set from `prisma/seed.ts` (hardcoded demo values like 1248, 874, 516) and was never incremented when a real user enrolled via `POST /api/progress` (`action: "enroll"`). Every course's displayed enrollment count has been permanently stale/fake since the first real signup, which directly conflicts with `soul.md`'s "Hindari data atau kemampuan palsu" principle. Fixed by incrementing `studentsCount` inside the existing enroll transaction, only on genuinely new enrollments (not re-enroll no-ops). No unenroll feature exists anywhere in the codebase, so no decrement path was needed for symmetry. Note: this stops the count from drifting further but doesn't retroactively correct courses that already accumulated real enrollments under the old code — that would need a one-time backfill (`studentsCount = COUNT(enrollments)` per course) run directly against the production database, which is out of scope for an autonomous code change. Verified with typecheck, lint, `dup:check`, and a full production build (54/54 routes).
- **2026-07-26 [Phase 11 - Forum Reply Notifications]**: Second autonomous feature cycle. Same notification-gap pattern as Phase 10, found in the discussion forum this time: `POST /api/forum/reply` created the reply and bumped the thread's `updatedAt`, but never notified anyone — a thread's original author and any other participants had no way to know someone replied except by manually revisiting the thread. Added a `Notification` (type `FORUM_REPLY`) for the thread author plus every distinct prior replier (excluding whoever just replied), linking to `/forum/[threadId]`. Also switched the recurring feature-development routine's merge policy to fully autonomous: once a cycle's PR passes the real quality gates (typecheck/lint/dup-check/build/smoke via GitHub Actions), it merges itself — Netlify/Vercel checks are ignored for merge decisions per the project owner's explicit instruction to deprioritize deployment while a VPS migration is pending. Verified with typecheck, lint, `dup:check`, and a full production build (54/54 routes).
- **2026-07-26 [Phase 10 - Assessment Grading Notifications]**: Started an ongoing autonomous feature-development cycle (recurring every 6 hours) to keep expanding the LMS while deployment/database work is paused. First gap found: when a mentor grades an essay/assignment (`POST /api/mentor/evaluations/[attemptId]/grade`), the student was never notified — the `Notification` model and bell UI already exist and are used for attendance/broadcast/material events, but grading completion didn't create one, so a student had no way to know their async-graded work was reviewed except by manually revisiting the course. Added a `Notification` (type `ASSESSMENT_GRADED`) inside the existing grading transaction, worded differently for pass/fail, linking to `/riwayat`. Also found `/riwayat` (the student learning-history timeline) showed evaluation entries as generically "Selesai" even while an essay was still `PENDING_GRADE` awaiting the mentor, never linked back to the course, and never surfaced the mentor's written feedback at all despite it being captured server-side. Fixed all three: a distinct "Menunggu Penilaian" state, a link to the course, and the feedback text rendered as a quoted note. Verified with typecheck, lint, `dup:check`, and a full production build (54/54 routes, `/riwayat` bundle size unchanged).
